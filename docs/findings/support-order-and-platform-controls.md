# Support ordering and cross-platform controls

Status: implementation and diagnostic evidence; **not a release approval**. Core candidate: official `7f945cdf5e5e1a8ec4854fda7acc734a959356e7`. The frozen 0.20.0 successor and all previous approval decisions remain unchanged.

## Supporting event ordering

Core flattens semantic support by observation UUID. Different storage implementations allocate those UUIDs differently, so the same evidence set can be reported in different orders. Source-authority and authoritative-correction metrics compare supporting event IDs as sets. The CogKura Bench adapter now maps the exact observation revisions to benchmark IDs, removes duplicates, and sorts IDs lexicographically in those two observation types. This is a presentation contract for evidence membership; it does not imply chronology or ranking, alter Core or change retrieval.

Against the official-origin candidate, the [raw four-backend report](data/core-0201-support-order-threeway.json.gz) passes for memory, SQLite, SQLite reopen and PostgreSQL, including the mini PostgreSQL repeat. The full local successor replay changes nine query/profile signatures compared with the unmodified adapter. Every changed field is an ordering of supporting event IDs; all metrics and recorded-use signatures are unchanged. The [exact before/after review](data/core-0201-support-order-before-after.json.gz) retains the IDs and fingerprints. Its captured adapter patch SHA-256 identifies the source under test. This behavior change is explicit and the old gold remains intact; the additional fingerprints and previously unapproved history differences have not been approved. The [successor raw report](data/core-0201-support-order-successor.json.gz) still fails its gate with 12 changed query/profile signatures across four runs: these nine order-only changes plus the existing three history differences. Source-history v2 passes 191/191 with PostgreSQL parity.

## Cross-platform numerical evidence

The earlier official 0.20.1 Linux matrix was compared to the original Mac 0.20.0 successor. Outside the three history queries, there were five additional changed query/profile signatures on Python 3.12–3.15 and 14 on Python 3.11. All those changed query fields were numeric, with maximum absolute difference `4.440892098500626e-16`. On Python 3.11, 61 aggregate metric fields across 16 run fingerprints also differed by at most `2.220446049250313e-16`. These figures diagnose the captured evidence; they are not a proposed universal tolerance.

To distinguish a candidate regression from platform effects, the unchanged official 0.20.0 commit `b30433c9577fe2493072e442b0f4ea307f342fcf` was run using the [same hosted workflow and Bench commit](https://github.com/cogkura/cogkura-bench/actions/runs/44829402704) as the [0.20.1 candidate](https://github.com/cogkura/cogkura-bench/actions/runs/44808046114). For each Python version 3.11–3.15, Python build string, SQLite version, hash seed and fixture seed match; both environments are Linux x86-64 with glibc 2.43, although their kernel and cloud-provider identifiers differ for four pairs. These are separate hosted runs, not identical hosts.

Comparing each Linux control directly with its 0.20.1 counterpart yields exactly the same three history queries (6, 5 and 8 changed fields respectively), and no aggregate metric or recorded-use differences. Thus the additional differences against the Mac frozen reference were also present in the 0.20.0 Linux controls and are not attributable to the 0.20.1 candidate in this experiment. Their precise arithmetic cause remains unestablished. All five control jobs failed the original strict frozen and raw backend gates. See the [complete pairwise review](data/core-020x-linux-platform-control.json.gz) and retained raw `core-0200-b30433c-hosted-*` and `core-0201-7f945cd-hosted-*` reports.

`scripts/compare_platform_controls.py` validates both official Git identities, runtime versions, fixture seeds, query and use fingerprints, and exact populations before recording full differences. It reports both platform strings and never changes the frozen gate, rounds values, or approves differences. The two input reports must come from the same verified Bench commit and equivalent fixture configuration; the operator must verify and retain that provenance independently because the original raw reports do not encode the Bench commit. The two hosted runs above both used Bench `7f122dd3fbfb2d731feb99484f8980e8199dd080`.

## Proposed same-run comparison contract

For future platform-independent investigation, the opt-in paired diagnostic runs the exact official 0.20.0 reference and candidate on the same runner, Python build, SQLite version, seeds and clean Bench checkout. `--capture-bench-provenance` records the Bench commit and refuses a dirty checkout or a Bench module imported from elsewhere; it checks the checkout again at completion. `--require-paired-provenance` rejects different platform strings, runtimes, seeds, commits, missing provenance, failed diagnostics, failed source checks and absent PostgreSQL parity. Both reports' query and use fingerprints and the full run populations must validate against their details. It compares all fields exactly, without numerical tolerance. The checkout provenance is not cryptographic attestation of the runner or a guarantee that different runs used the same physical hardware.

The standard Bench CI keeps the original 0.19.6 frozen and reviewed-order checks on the pinned `7f122dd` Bench checkout, and independently requires exact raw backend parity using the current adapter. The prior gold and approval manifests are not rewritten.

The manually dispatched `paired-candidate-diagnostics.yml` performs both runs sequentially in one hosted job. Its output is labeled diagnostic and unapproved; a successful diagnostic job only means the evidence was captured and compared, not that its differences are acceptable. The original strict frozen workflow and gold remain unchanged, and no paired result overrides a release gate. Any policy making a paired result authoritative would require a separate review, including its pinned reference, clean Bench identity, history differences and approval scope.

## Mixed-time historical reconstruction

Core `7f945cd` fails closed when a current episode or semantic aggregate includes evidence after the requested cognitive time. This prevents the original exception and future-derived candidates, but can omit earlier known material. It is not a complete historical reconstruction. The episode store exposes current rows rather than episode snapshots; the exact observation-revision read deliberately excludes current-only fields such as source type, and hash-only retention may leave no recoverable content. Re-encoding the latest observations or clipping timestamps would therefore invent historical content or metadata for some records. A complete fix needs a separately specified snapshot/reconstruction contract, retention and missing-history behavior, revision/late-arrival coverage and backend migration assessment. The current release gate has not been changed to treat the limitation as resolved.

## Release implications

The raw backend discrepancy is fixed locally in Bench, subject to reviewing the nine explicitly changed frozen query signatures. The existing three correction-history differences remain unapproved. Exact cross-platform fingerprint portability still needs a deliberately reviewed comparison contract or platform-specific reference strategy; this investigation has not changed numerical tolerances or the release gate. Core 0.20.1 remains unreleased.
